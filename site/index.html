One file · HTTPS by default · No config language

Everything necessary to do one thing well.

Servette is a production nanoserver: a single readable Python file that serves a static site on the public internet with a trusted certificate that renews itself, security headers on every response, rate limiting, and a hardened service that survives reboots.

No configuration language to learn, and a single dependency it installs for you. Copy one file to a server, run it, follow the wizard, done.

The space between

Most ways to serve a site sit at an extreme.

General-purpose servers do everything, once you have configured them. Development servers do one thing and stop there. Managed platforms do it for you, on terms that are theirs. Servette aims at the space between.

General-purpose servers

nginx, Apache, Caddy. Any site, at any scale — after you have learned a configuration language and taken a large system on trust.

Development servers

http.server and friends. Perfect while you build; by their own documentation, not built to face the internet.

Managed platforms

GitHub Pages, Netlify, Vercel. They host it for you, on their infrastructure, under their terms and their limits.

Servette

Do everything necessary to do one thing well: host a static site you own, securely, on a server you control.

Fit

Who it is for

You want to understand your server

One readable file with no hidden machinery, rather than a large system you configure and take on trust.

You have a real site that needs a real server

Trusted HTTPS that renews itself, and a hardened service that survives reboots — not a terminal you cannot close.

You want to own what you serve

Your own server, your own certificate, behind a password if you want one. No platform terms in between.

You are on a Raspberry Pi

Designed with the Pi in mind. If you can SSH in and run a Python script, you can have a real HTTPS site live in minutes.

Servette is not for dynamic applications, server-side rendering, or anything that needs to run code per request. It serves files — anything that runs in a browser, from a portfolio to a serious client-side app — and deliberately stops there.

Getting started

How to use it

Servette needs Python 3.11 or newer and a server you can SSH into. There is nothing for you to install beyond the file itself: it pulls its one dependency, cryptography, on first run. No configuration language, and nothing to build.

Copy the file

One file and the folder you want to serve.

# on your server
curl -O https://raw.githubusercontent\
.com/andy-emerson/servette/main\
/servette.py

# your site goes beside it
mkdir site

Run the wizard

It asks for a domain, a folder, and an email.

python3 servette.py

servette> setup

Leave it running

Installed as a system service, it restarts itself.

servette> enable
servette> status

running · https://example.com

The wizard issues a Let's Encrypt certificate, redirects plain HTTP up to HTTPS, and installs a systemd service so the server comes back after a reboot. Renewal happens on its own — a watchdog checks the certificate on a timer and renews it well before it expires.

Serving over a self-signed certificate works too, for a local network or a machine without a public domain. The browser will warn once; everything else behaves the same.

Publishing

Updating your site

Edit files in the served folder and the change is live on the next request — there is no build step and no restart. For a site you publish from somewhere else, Servette can fetch a signed bundle on request.

Edit in place

Change a file in the served folder. The next request sees it. Nothing to reload, nothing to invalidate.

Pull a signed bundle

Point a site at a publish channel, then run pull. Servette fetches the bundle, verifies its signature, and swaps it in atomically.

Roll it back

restore-site undoes the last pull. restore undoes the last update to Servette itself.

Publishing is always operator-triggered — from the shell, over SSH. No HTTP request can cause Servette to write anything. See How it Works for why that line is drawn where it is.

Architecture

Four regions, one boundary, nothing that writes on request

Servette is one file, but not one undifferentiated mass. It divides into four regions, and the line between two of them is the property the whole design rests on: no HTTP request ever reaches code that writes.

control flow
writes (thick)
reloads Server's TLS on renewal
dependency / delegation (dotted)

The invariant

Requests read. Only the operator writes.

SERVER is the only region a network request can reach, and it is read-only. It selects a site, applies rate limits, checks a password if one is set, and serves a file. It has no path to a write — not to disk, not to configuration, not to the site's contents.

SHELL is the only region that writes, and it is reachable only by an operator over SSH. Adding a site, pulling new content, updating Servette itself, rolling any of it back — all of it lives here, behind an interactive prompt.

SYSTEM is what runs on its own schedule rather than on anyone's request: the bootstrap sequence, the service lifecycle, and the certificate watchdog that renews on a timer and hands the fresh certificate to the running server.

INIT is the entry dispatch and the module preamble — the ninety lines that decide which of the other three you get.

Read the diagram for the consequence: there is no arrow from anything a visitor touches into anything that writes. That is not an access-control rule that could be misconfigured; it is the shape of the code.
